## What was wired

1. **The server's clock, in the status message** — `tools/scan_server/main.cpp`,
   `BuildStatusJson`: a `server_now_ms` field from the same `NowMs()` that stamps the
   frames' `t_capture`/`t_server`. Every status (~1 s) re-estimates the offset, so a clock
   step cannot leave a stale correction in place. The frame envelope already carried the
   sequence (`seq`) and both timestamps, so nothing new was added per frame.
2. **The arithmetic** — `ui/frame_age.js` (new, pure, no DOM):
   `age at receipt = (local wall at receipt + server-clock offset) − t_capture`, then
   `frame age = age at receipt + (render perf − receipt perf)`. The local leg uses
   `performance.now()` so a wall-clock jump cannot corrupt a delta; only the offset
   estimate uses the wall clock.
3. **The HUD** — `ui/app.js`: the tracker is fed from `handleStatusMessage` and the cloud
   frame path, the render delay is closed out in `draw()` at the point the frame goes to
   the GPU, and `updateHud()` renders p50/p95 plus a sparkline of the last 60 s.

## What it measures — and what it does not

`t_capture` is **the server tick's read time**, not a device capture timestamp (the tick
passes `NowMs()`; see `docs/recomp/log/2026-10-19-row-136-pipeline-map.md` — the SDK
frame timestamp is one of the things we do not read). So this is **tick → render**, and
the HUD label says so rather than pretending to measure the scanner's own leg. The
device-capture leg is not observable in this pipeline today; that is #136's stage-1 gap,
not a shortcoming of this metric.

The offset is estimated from the status message, so it carries that message's one-way
transit. On loopback that is sub-millisecond. The number is an estimate and the label
names the clock it is on.

## The arithmetic check (device-free)

`ui/frame_age_test.js`, registered with ctest as `ui_frame_age_test` (skipped when node is
absent). Eight arithmetic checks plus an end-to-end leg:

| check | result |
| --- | --- |
| age at receipt = (local wall + offset) − t_capture | PASS |
| no server clock yet → `null`, not a garbage number | PASS |
| frame age = age at receipt + local render delay | PASS |
| a render delay cannot be negative | PASS |
| the offset is re-estimated on every status message | PASS |
| percentiles are nearest-rank, like `perf_window.h` | PASS |
| the rolling window drops samples older than 60 s | PASS |
| the sparkline maps oldest→left, newest→right, 0 ms at the floor | PASS |
| **synthetic end-to-end**: status carries `server_now_ms`, a frame yields a real age | PASS |

The end-to-end leg starts `scan_server --synthetic` on a free port, reads the status
message's `server_now_ms`, reads a cloud frame's `t_capture`, and computes the age exactly
as the page does. The value in the raw log, on local loopback, is **`p50 0.2 / p95 0.2
ms`** — that is the number this record stands behind; the check prints a fresh one on every
run, so re-derive it rather than quoting this line if it matters.

## The browser capture, and its caveat

The HUD text in the raw log was read back from the live page (`?port=18098`, `webgl2`,
against `scan_server --synthetic 18098`). That browser runs behind the tool's proxied
transport and its socket arrives in bursts (`data 0.0 fps` between them), so the captured
age is **seconds** — 1674 / 3084 ms in the capture in the raw log — where the same
binary on local loopback is under 1 ms. That is not a defect to hide: it is the metric reporting a bad path, which is the
whole reason for having it. The headless tab also throttles `requestAnimationFrame` to zero, so the
page's render loop was driven with timers for the capture (a normal visible window runs it
on rAF). The screenshot tool needs a visible desktop window, so this record carries the
HUD text read from the live page rather than an image.

## What a device run would see

The same HUD line, with `t_capture` = the tick's read time on a real session, so the
number would include the vendor getter and the 20,000-point decimation (#136 stage 3-4)
plus the broadcast and the browser's queue. It would answer "how stale is the cloud the
operator is looking at" — which is the number #113 should hold itself to. That run is not
this row; `--live` is the existing #112/#115 harness and was not started here.
